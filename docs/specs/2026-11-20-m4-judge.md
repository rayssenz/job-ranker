# Milestone 4: judge

Status: approved on 2026-11-20

## Problem

The rules of milestone 2 drop only the postings that certainly cannot fit. What is left still holds many postings that a person would rule out after reading the description: the wrong skills, too many years of experience, a language asked for in the text. Reading every description by hand takes the time the tool is meant to save.

## What this milestone adds

- A judge that reads one posting and the profile and answers yes or no, with short reasons.
- A stored verdict per group of linked postings, so a posting is judged once and again only when it, the profile or the prompt changes.
- A command, `jobrank judge`, that judges the postings that passed the rules and have no current verdict.
- The verdict on the dashboard cards.

## Cost

The judge calls Claude Code's non-interactive mode (`claude -p`) on the machine. It uses the plan login of Claude Code and no API key.

Checked on 2026-11-20:

- The vendor's help page "Use the Claude Agent SDK with your Claude plan" states that `claude -p`, when signed in with a plan, draws from the usage limits of the plan. A separate billing for this mode was announced for June 2026 and then paused.
- One test call with the flags below returned a structured answer in about 2 seconds, with no API key set.

A call can still be billed on top of the plan in two cases:

1. A model API key or token is set in the environment. Claude Code then uses it in place of the plan login, and the call is billed per token.
2. The account has usage credits turned on. A call made after a plan limit is reached is then billed per token and does not fail.

The program guards against the first case and cannot see the second:

- The command refuses to start when the environment holds a model API key or token, or selects a cloud provider, or when `claude auth status` does not report a plan login.
- Usage credits are an account setting, outside the program. They have to be turned off in the account for judging to be free of extra cost in every case. The README says so.
- When the plan limit is reached, the call fails. The run then stops, stores no verdict for that posting and says that the limit was reached. The next run continues where this one stopped.

Judging shares the plan limits with every other use of Claude on the same account. A run that uses the limit up blocks that other use until the limit resets. The run limit below keeps one run small.

Every answer of `claude -p` carries a cost figure. On a plan login it is a notional figure, computed from list prices. It is not a charge. It is stored to compare prompts in milestone 6 and is shown nowhere as money owed.

## Judge

One interface, `judge(posting, profile) -> verdict`, with two implementations in this milestone.

`ClaudeCodeJudge` runs `claude -p` as a subprocess, once per posting:

- `--output-format json` with `--json-schema` for the answer
- `--tools ""`, so the model can read no file and run no command
- `--no-session-persistence` and `--setting-sources ""`, so no session is saved and no user or project settings, hooks or servers are loaded
- `--system-prompt` with a fixed text, and `--model` with a pinned model
- the working directory is an empty temporary folder, and the prompt goes in on standard input
- a time limit per call

The pinned model is a small, fast one, because it uses the least of the plan limit. `--model NAME` on the command picks another. The evaluation of milestone 6 measures whether a larger model judges better.

`FakeJudge` returns fixed answers. The tests and CI use only this one. CI never calls a model.

`ReplayJudge` of the technical design comes with the evaluation in milestone 6.

### What the judge reads

From the posting: title, company, location, remote flag and description. A description above a fixed length is cut, and the verdict records that it was cut.

From the profile: `roles`, `skills`, `notes`, and also `languages` and the two level word lists, because a language or a level asked for only in the description was left to the judge by milestone 2.

The posting text comes from a third party. It is passed as data between fixed markers, and the system prompt says that nothing inside the markers is an instruction. With no tools, a posting that tries to give orders can at worst get a wrong yes or no for itself.

### Answer

```json
{
  "decision": "yes",
  "reasons": ["Asks for Python and SQL, both in the profile"],
  "matched": ["Python", "SQL"],
  "missing": ["Airflow"]
}
```

`decision` is `yes` or `no`. `reasons` holds one to three short sentences. `matched` and `missing` list the requirements of the posting that the profile covers and lacks. An answer that does not fit the schema counts as a failure.

Yes or no is used and not a score from 1 to 5, as in the technical design. The dashboard orders the yes postings by fewest missing requirements.

## Linked postings

A group of linked postings is judged once, on the newest posting in it that passed the rules. The verdict counts for the whole group.

## Storage

The schema version rises from 3 to 4. A new table `verdicts` holds, per judged posting: the content hash, the hash of the profile fields the judge reads, the prompt version and the model it was computed for, the decision, the reasons, the matched and missing lists, whether the description was cut, the token counts, the duration, the notional cost and the time.

A database of version 3 is upgraded in place when it is opened, as in decision record 0008. Postings, rule results and decisions are not changed.

A verdict is current when its content hash, profile hash, prompt version and model equal the present ones. A change of a profile field that only the rules read does not make a verdict stale.

## Command

`jobrank judge` applies the rules first, then judges the groups that passed, have no current verdict and have no decision, newest first.

- `--limit N` sets how many postings one run judges at most (default 40). A larger backlog takes several runs.
- `--model NAME` picks another model than the pinned one.
- `--dry-run` prints how many postings wait, and judges nothing.
- The run prints one line per posting as it goes: company, title and yes or no. At the end it prints the counts of yes, no and failed, and how many still wait.
- A failed call (time limit, broken answer, error from Claude Code) is counted, stores no verdict, and the run goes on. Three failures in a row stop the run. A reached plan limit stops the run at once.
- The command refuses a database file that does not exist, a missing profile, a missing `claude` program, and the cases named under Cost.

The command sends each posting and the judge's part of the profile to the model provider through Claude Code. It sends nothing else and nothing anywhere else.

## Dashboard

- A card with a verdict shows a yes or no mark and the reasons. A card without one shows "not judged yet".
- "To review" gets a switch "only yes". It is off when the dashboard opens, until the evaluation shows how far the judge can be trusted. With it on, cards are ordered by fewest missing requirements, then newest. With it off, the order stays newest first and every card that passed the rules is shown, so a wrong no hides nothing.
- A stale verdict is shown as "not judged yet".
- The dashboard never starts a judging run. It only reads verdicts.

Reasons are text written by a model about text from a third party. They are escaped like every other text on the page.

## What is private

The verdicts, the reasons and the matched and missing lists stay in the database on the machine. Messages and logs hold counts and fixed words. The lines the command prints to the terminal show company and title, as `jobrank list` does. The repository holds the judge, the prompt, the fictional example profile and tests with made-up postings and made-up answers.

## Non-goals

- Measuring how good the judge is. Marked cases come in milestone 5, the evaluation and `ReplayJudge` in milestone 6. Until then the prompt is a first version and is not tuned.
- A shortlist and its delivery. That is milestone 7.
- A score, or an order among the no postings.
- Judging on a schedule. The command is started by hand.
- Several calls at the same time.
- Another model backend. The interface allows one later.

## Acceptance criteria

1. With `FakeJudge`, `jobrank judge` stores a verdict for every group that passed the rules and has no decision, and judges each group once.
2. A second run with nothing changed judges nothing. After a change of the posting text, of a profile field the judge reads, of the prompt version or of the model, the affected postings are judged again. A change of a profile field that only the rules read judges nothing again.
3. `--limit N` judges at most N postings, newest first, and the next run goes on with the rest. `--dry-run` judges nothing and prints the number waiting.
4. A failed call stores no verdict and the run goes on. Three failures in a row stop the run with exit code 1. A reached plan limit stops the run at once with a message that names the limit.
5. The command refuses to start, with a short message and exit code 1, when a model API key or token is set, when a cloud provider is selected, when `claude auth status` reports no plan login, or when `claude` is not installed.
6. `ClaudeCodeJudge` builds the command line with every flag listed above, runs it in an empty folder and passes the prompt on standard input. A test checks the exact arguments against a stand-in program.
7. An answer that is not valid JSON, has no structured part or does not fit the schema is a failure and stores nothing.
8. A posting whose text holds an instruction is passed between the markers unchanged, and the system prompt is the same for every posting.
9. A description above the length limit is cut, and the verdict records it.
10. A version 3 database with postings, rule results and decisions opens, is upgraded to version 4 and keeps every row.
11. The dashboard shows the mark and the reasons on a judged card and "not judged yet" on the others. "only yes" shows the yes cards ordered by fewest missing requirements. With the switch off, a card with a no is still shown.
12. Reasons that hold HTML are shown as text.
13. No posting text, profile value or reason is written into a log or an error message.
14. The tests and CI call no model and need no login.
