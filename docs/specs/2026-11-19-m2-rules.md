# Milestone 2: rules

Status: approved on 2026-11-19

## Problem

Milestone 1 stores every posting that the sources return. A company feed returns all open jobs of that company, in every place and at every level, so most stored postings cannot fit one person. Nothing separates the postings worth a closer look from the rest.

## What this milestone adds

- A private profile file that says which places, levels and languages fit.
- Fixed rules that drop a posting when it certainly cannot fit, with a reason code for each drop.
- A stored result per posting, so a posting is checked once and again only when it or the profile changes.
- Two commands: `jobrank rules` applies the rules, `jobrank list` prints the postings that passed.

No model is involved. The same posting and the same profile always give the same result.

## Profile

`profile.yaml` in the repository root, not committed. `config/profile.example.yaml` is a fictional example. This milestone reads these fields:

```yaml
places: [Lisbon, Porto]          # a posting in one of these places fits
remote:
  accept: true                   # remote postings can fit
  places: [Portugal, Europe]     # only when the location names one of these; empty accepts any
levels:
  accept: [junior, graduate, intern, internship, working student]
  reject: [senior, staff, principal, lead, head, director]
languages: [English, Portuguese] # languages the person can work in
avoid: [gambling]                # words in a company name or title that rule a posting out
title_words: []                  # when not empty, a title must hold at least one of these
```

All word lists belong to the profile. The program holds no list of places, levels or role words, because such a list describes one person's search. The other profile fields of the technical design (skills, notes for the judge) are read from milestone 3 on and are ignored here.

A missing profile stops both commands with a message that points to the example file. An unknown field or a wrong type is rejected with the name of the field.

## Rules

Every rule is a pure function of one posting and the profile. It returns pass or one reason code. Words are compared in the normalised form of milestone 1, as whole words, so `intern` does not match `internal`. A phrase of several words matches when its words follow each other.

| Code | The posting is dropped when |
|---|---|
| `place` | the location names no place from `places`, and the posting is not an accepted remote posting. A remote posting is accepted when `remote.accept` is true, the posting is marked remote, and its location names a place from `remote.places` or `remote.places` is empty. |
| `level` | the title holds a word from `levels.reject` and no word from `levels.accept` |
| `language` | the title asks for a speaker of a language that is not in `languages`, written as a language name followed by `speaking` or `speaker`, or the German forms `sprachig` and `sprechend` |
| `avoid` | the company name or the title holds a word or phrase from `avoid` |
| `title` | `title_words` is not empty and the title holds none of them |

A rule drops a posting only when the mismatch is certain:

- An empty location passes the place rule.
- A title with no level word passes the level rule.
- A language asked for only in the description is left to the judge of milestone 3.

All rules are evaluated for every posting, and every reason code that applies is stored. The language names the rule knows are a fixed public list in English and German.

## Linked postings

A posting from the search source can be linked to a feed posting of the same company and title in another place. The rules check every posting, linked or not. A group of linked postings passes when any posting in it passes, and `jobrank list` prints the group once, with the posting that passed.

## Storage

The schema version rises from 1 to 2. A new table `rule_results` holds, per posting: the content hash and the profile hash the result was computed for, the version of the rules, pass or fail, the reason codes and the time.

A database of version 1 is upgraded in place when it is opened: the new table is added and the version is set, in one transaction. The stored postings are not changed. A database with a version above 2 is refused, as before.

A posting is checked again when its content hash, the profile hash or the rules version differs from the stored result.

The Ashby adapter stores the secondary locations of a posting after the primary one, so a job offered in several places is not dropped for its first place. The location is part of the content hash, so these postings are recorded as changed once on the next run.

## Commands

`jobrank rules` checks every posting without a current result and prints one line per reason code with its count, and the number of postings and groups that passed.

`jobrank list` prints the groups that passed, newest first: company, title, location and link. `--days N` limits the list to postings first seen in the last N days. `--limit N` limits its length (default 50).

Neither command sends a request.

## What is private

The profile, the reason codes and the output of both commands stay on the machine. The repository holds the rules, the fictional example profile and tests that use only made-up postings.

## Non-goals

- Judging whether a posting that passed is a good match. That is milestone 3.
- Ordering by fit. The list is ordered by date.
- Reading a required language or the years of experience from the description.
- A stored employment type.
- The dashboard. It is a milestone of its own after this one.

## Acceptance criteria

1. With the example profile, a posting in an accepted place passes, and a posting in another place is dropped with `place`.
2. A location that names several places passes when one of them is accepted.
3. A remote posting passes only as described for `remote.accept` and `remote.places`.
4. A title with a rejected level word is dropped with `level`. A title with an accepted and a rejected word passes. A title with no level word passes.
5. A level word inside a longer word does not match.
6. A title that asks for a speaker of a language outside the profile is dropped with `language`. The same phrase in the description alone does not drop the posting.
7. A posting whose company name or title holds an avoid word is dropped with `avoid`.
8. With `title_words` set, a title without any of them is dropped with `title`. With the list empty, the rule passes every title.
9. A posting that fails several rules has every code stored.
10. A linked group passes when one of its postings passes, and the list shows the group once.
11. A second `jobrank rules` run with nothing changed checks no posting. After a change of the profile, or of a posting, the affected postings are checked again.
12. A version 1 database with stored postings opens, is upgraded to version 2 and keeps every posting, version and run log row.
13. A missing or malformed profile stops the commands with a short message and exit code 1.
14. Reason codes are fixed words. No posting text and no profile value is written into a message or a log.
15. `profile.yaml` is ignored by Git, and the repository check fails when a profile other than the example is tracked.
